# SessionMaxxing

Local-only dashboard whose single goal is to get the most out of a Claude subscription (Pro, Max, Team or Enterprise): fill five-hour session windows that would otherwise go unused with queued Claude Code tasks, while keeping the weekly limit on pace so interactive work never gets cut off.

## Stack

React + TypeScript + Next.js (App Router, static export), Tailwind CSS, Recharts, Fastify, Vitest, Biome, pnpm. Node 22.12+.

Four routes: `/` (Overview), `/analytics/` (Analytics), `/queue/` (Task queue), `/runs/` (Runs); the lite edition serves Queue and Runs only (see Lite edition). Fastify serves the static export from `dist/client`.

## Layout

- `app/` is the Next.js App Router tree. Route folders hold only `page.tsx`; `layout.tsx` and `styles.css` sit at the root. `output: "export"` with client-side fetching means `loading.tsx` never renders, so page skeletons live in `app/components/Skeletons.tsx`.
- `app/components/` holds feature components grouped by route (`overview/`, `analytics/`, `queue/`, `runs/`); components used by more than one route sit at the folder root. `app/components/ui/` is shadcn-generated and edited only through the shadcn CLI.
- `app/hooks/` holds React hooks; `app/lib/` holds pure client logic (API client, time helpers, chart series, queue ordering, cache) that tests import directly without rendering.
- `server/` is the Fastify process, a flat module set compiled by `tsc -p tsconfig.server.json`; `shared/types.ts` is the contract between server and client. `server/data-directory.ts` resolves the data directory and performs its one-time move, `server/environment.ts` validates the host, edition, allowed hosts, work-directory root and time zone, and `shared/local-time.ts` holds the zone-explicit day, hour and offset helpers both sides use. `server/restart-methods.ts` stores each work directory's restart method, `server/restarts.ts` the restart records, `server/restart-executor.ts` runs them, and `server/restart-migration.ts` converts the old host watcher's state once.
- `scripts/` is the CLI queue helper; `tests/` is Vitest with `helpers.ts` and `fixtures/`.
- Imports inside `app/` use the `@/` alias (`@/app/...`, `@/shared/types`); `server/` and `tests/` use relative `.js` specifiers because the server runs under plain Node with no alias rewriting. No barrel files.

## What the dashboard knows

- **Official usage** comes from Anthropic's own endpoint, `GET https://api.anthropic.com/api/oauth/usage`, called with the OAuth token Claude Code stores in `~/.claude/.credentials.json` (`claudeAiOauth.accessToken`), the `anthropic-beta: oauth-2025-04-20` header, and Claude Code's own `claude-cli/<version> (external, cli)` User-Agent. This is the same data as Claude Code's `/usage` panel: `five_hour`, `seven_day`, and per-model weekly windows under `limits[]` (`kind: "weekly_scoped"`, `scope.model.display_name`, `percent`, `resets_at`). The token is read at fetch time and never returned by any dashboard route. When the token expires within five minutes, or the endpoint answers 401, `server/claude-usage.ts` rereads the file (another Claude Code process may already have rotated the refresh token), refreshes it through the refresh grant at `platform.claude.com/v1/oauth/token`, and writes the new credentials back with one atomic rename at mode 0600 so Claude Code picks them up. The token endpoint answers 429 to any other User-Agent. A refused refresh shows as the usage error and asks you to run `claude`.
- The server polls every five minutes, keeps the last good snapshot when a fetch fails, and appends each snapshot to `usage-samples.jsonl` in the data directory. Samples are kept for 90 days and power the session-window timeline, the weekly-pace chart, and the plan score.
- **Plan score** (`GET /api/plan-score`) measures how close usage gets to two goals: every five-hour window near 100% and the weekly limit near 100%. Session coverage of a local day (in the server's time zone) = Σ(window peak % × hours of that window inside the day) ÷ elapsed hours of the day, so back-to-back windows at the cap score 100. A finished week scores its final weekly %; the open week scores used % ÷ elapsed pace, capped at 100. The open week is the window the latest sample reports; another open window, left by an earlier login, is dropped. The plan score is the mean of the last seven days' session coverage and the current week's score. Days before sampling began are null, never zero.
- **Local activity** comes from `~/.claude/projects/*/*.jsonl`, subagent transcripts under `~/.claude/projects/*/<session>/subagents/*.jsonl`, Workflow agent transcripts under `<session>/subagents/workflows/*/agent-*.jsonl`, and `~/.claude/history.jsonl`: active minutes, responses, model and project mix, heatmap, cumulative chart, quiet-window ranking. Content never reaches the browser.
- **Activity source** is attributed per assistant record, never by time overlap. A queued Claude task is launched with `--session-id <uuid>`; that id is stored in the run's server-side metadata and any record (including subagent records) carrying it counts as *Dispatched tasks*. Records with `entrypoint: "cli"` count as *Local Claude Code*. Headless records not tied to a run, and records without provenance (older runs, missing fields), stay *Unattributed*. The official quota has no source breakdown, so claude.ai and laptop usage appear only as *Other* with no number; splitting them would need a provenance-tagged import of the laptop's own transcript metadata, which does not exist yet. Session ids never reach the browser.

## Task cost

A task stores the **weighted tokens** its whole run is expected to produce, every model and subagent included, so the number survives a plan change. A weighted token counts output once and uncached input, cache writes and cache reads at their list-price ratio to the family's output price (`FAMILY_PRICING` and `weightedTokens` in `shared/types.ts`). `"auto"` has a Haiku estimator read the prompt and past runs before the task is stored, and a failed estimate is an error, never a default. `server/calibration.ts` fits the session percent one million weighted tokens cost per model family by non-negative least squares over the last 14 days of official five-hour windows (`peak %` against the weighted tokens produced inside the window), skipping windows the meter censored at 100% and windows under 8%. A family with under a tenth of the sample's weighted tokens, or a zero fit, is priced off the best-covered family at their list-price ratio, and a cheaper family's own rate is capped at that ratio. Every session percent shown — a task's expected cost, a finished run's cost — is derived from tokens at the current rates, and the Claude gate waits while no window can be fitted. A finished Claude run stores the weighted tokens of its own session, read from its transcript and its subagents' and Workflow agents' transcripts, instead of the session-meter delta, which any concurrent work contaminated.

## Dispatch policy

With the queue switch on (persisted in `queue.json` across restarts), the server runs up to `maxConcurrentRuns` queued tasks at once (default 2, range 1 to 4; 1 is the old serial behaviour); every task still running at a restart is marked failed. A Claude task is **ready** only when all hold:

1. A run slot is free.
2. An official snapshot exists and is under fifteen minutes old, and was fetched after the last run ended.
3. Session utilization plus the session points held for running Claude tasks is at or below `100 − reserve`, where the reserve is `sessionReservePercent` (default 25%) inside quiet hours and `busyHoursReservePercent` outside them. An expired session window counts as 0%; a failed gate names which reserve applied when the two differ. A Claude task also needs headroom for its own expected session cost, `session % + points held for running tasks + expected cost ≤ cutoff`, where the expected cost is the task's own `tokens` priced at the fitted session rates until a completed run has been measured, then the largest session percent among that task's completed runs (failed and cancelled runs never set the price). An expected cost above the cutoff is capped at the cutoff, so such a task starts only in an empty session instead of never.
4. Weekly utilization plus the weekly points held for running Claude tasks plus the task's own `runWeeklyCostPercent` is at or below `min(95, pace + weeklyMarginPercent)` where pace is the elapsed share of the seven-day window (default margin 10%).
5. For models matching `fable`, the same weekly rule applies to the Fable window when Anthropic reports one, counting only running Fable tasks and charging the task its own `runWeeklyCostPercent`.
6. With `busyHoursReservePercent` at 100 (the default) the queue keeps the whole session outside quiet hours, so a task without a preferred window starts only when the current local hour is among the `quietStartHours` (default 8) quietest five-hour starts, ranked from the last 30 days of interactive local activity (dispatched and unattributed records excluded) and cached for 10 minutes. Tasks with an explicit preferred window skip this rule. Until the ranking is computed, such tasks wait and say so. Below 100, quiet hours instead choose which session reserve applies and tasks run at any hour that has budget.

With the apply override on (`autoApply`, off by default), every dispatched prompt gains a closing instruction (`autoApplyInstruction(method, commit)` in `server/providers.ts`) telling the agent to edit the work directory in place, so a finished run is already live instead of waiting for review. What it says about git follows the task's `commit` option (on by default, and for tasks stored before the option existed; `--no-commit` in the queue helper and the form's Commit checkbox turn it off). With it on, the agent finishes with `git status`, stages only the files it created or changed, commits on the current branch with a subject that follows `CONVENTIONAL_RULES` in `shared/types.ts` (the rules `CONVENTIONAL_SUBJECT` checks), and runs `git push` when the branch has an upstream, reporting any push error; such a run records its own commits, so it needs no commit from the review flow. With it off, the agent ignores git entirely (no status checks, commits, stashes, branches, or worktrees). With the override off the option changes nothing. The instruction names the work directory's restart method. With None the dashboard restarts nothing after the run. With Docker Compose or Command the dashboard runs the method after the run ends, so the agent does not run `docker compose` or the command or redeploy the project itself. In every case the agent runs any other deploy the project needs (a Coolify deploy, the project's own deploy command) before it finishes, never restarts, recreates or stops the SessionMaxxing container that hosts the run, and reports the blocker and the command when its tooling is unavailable. Uncommitted changes never block a change or the restart. The stored task prompt is untouched; only the launched copy carries the instruction.

With the session keeper on (`keepSessionActive`, off by default), `server/session-keeper.ts` opens a new five-hour window as soon as the previous one has ended: when the latest official snapshot reports no session window (or one whose `resets_at` has passed), no Claude task is running, and the weekly window is under 100%, it runs `claude -p hi --model haiku --max-turns 1 --session-id <uuid>` from the home directory and lets it exit, then refreshes usage. It is independent of the queue: not a task, not gated by the queue switch, the reserves, or quiet hours. A second ping waits for a snapshot fetched after the last ping ended and at least ten minutes since it started, so a lagging endpoint cannot start sessions in a loop. Ping session ids are stored in `session-keeper.json` and count as *Dispatched tasks* activity; `GET /api/queue` carries `sessionKeeper` with the last start time and any error.

A Claude run that ends with Claude Code's usage-limit message (`You've hit your session limit`, `… 5-hour limit` or `… weekly limit`) is not a failure of the task: the run is stored as failed with the reason "Stopped at the usage limit", the task goes back to pending with no retry cap, and the normal gates hold it until the window resets. Its next run resumes the same Claude session (`--resume <session id>` with a continue prompt instead of the task prompt), so the session id and its *Dispatched tasks* attribution carry over; each run's tokens count only the transcript records written after that run started.

A Claude run that exits cleanly is completed only when every subagent its session wrote to during the run ended on a final reply (`stop_reason` `end_turn` or `stop_sequence`). `claude -p` exits when the lead agent's turn ends and interrupts any subagent still working, so a run that ends while it waits on a background subagent is stored as failed with the reason "Exited with N subagent(s) unfinished", and tasks that depend on it stay blocked until it is retried. A run whose subagent transcripts cannot be read fails the same way. Workflow agents are not checked, because their transcripts end on the structured-output tool call. To prevent that, every launched prompt, a resume included, ends with `HEADLESS_INSTRUCTION` (`server/providers.ts`): start subagents and long commands in the foreground and never end the turn while one is still working. The stored task prompt is untouched.

**Run now** overrides the usage gate and the schedule, never the slot bound or the locks. Settings persist in `dispatch-settings.json`.

A task can **depend on** other queued tasks (`dependsOn`, up to 20 ids). It waits until every one of them has completed, ahead of every other gate, and Run now refuses while one is unfinished. A dependency that failed or was cancelled keeps the task blocked with that reason until it is retried; deleting a task drops it from the tasks that depended on it, and a cycle is rejected when the task is saved.

**Eligible-time estimate.** This is the baseline model for the published product (SessionMaxxing); later phases keep it. A pending task's `eligibleAt` (`server/dispatch.ts`) is the first instant the live gate would admit it, found by walking the session from now: the pending Claude tasks queued ahead (minus those that depend on the task, directly or through a chain) start one after another, then the task itself. Each one starts at the first instant (now, or a later local hour boundary before the open window resets) whose hour's cutoff fits `used + cost`, the cost capped at that cutoff; the cutoff is `100 − sessionReservePercent` in a quiet start hour or when the queue runs only in quiet hours, and `100 − busyHoursReservePercent` otherwise. A task that fits nowhere before the reset waits for the next window, which starts empty (running tasks are assumed finished by then) and opens when its first task starts. With quiet hours only, the tasks ahead also start only in quiet start hours; the task itself also respects its earliest start, its preferred window, the weekly ceiling and, for Fable models, the Fable ceiling, each counting the points running tasks hold plus the task's own `runWeeklyCostPercent`. The estimate is never earlier than the live gate would admit, and with nothing queued ahead it is now exactly when `taskGate` is ready. It is null while the session rates are unknown, when the session reset is unknown and nothing fits, or when no allowed hour exists.

## Lite edition

- **Selection.** `SESSIONMAXXING_EDITION` is `full` or `lite`; unset is `full` and any other value stops startup. One build serves both and the server decides at start.
- **Pages.** Lite serves `/queue/` and `/runs/`. `/` answers 302 to `/queue/`, the Overview and Analytics files answer 404, and the client carries no guard.
- **Never started.** The history reader, `/api/analytics` and `/api/plan-score` (both 404), the token estimator, session-rate calibration and the quiet-hours ranking. The usage monitor and its samples, the session keeper, run review with commit, repository locks, dependencies, restart methods and Run now keep running as in full.
- **Gate.** `planLite` in `server/dispatch.ts` checks in order: a run slot is free; the official snapshot is fresh and newer than the last run; session utilization plus the held session points is at or below `100 − sessionReservePercent`; weekly utilization plus the held weekly points plus the task's own `runWeeklyCostPercent` is at or below `min(95, pace + weeklyMarginPercent)`. The wording is shared with the full gate, there is no Fable window, and `eligibleAt` is null.
- **Fixed hold.** Each running lite task holds `runSessionHoldPercent` session points (default 10) and `runWeeklyCostPercent` weekly points until it finishes. Polling folds real consumption into the snapshot while the hold stays, so the double count errs conservative as in full.
- **No tokens.** A task body with a `tokens` field is a 400, a lite task stores no token cost, and a finished lite run stores tokens null and no session cost.
- **Data directory.** A full start on a `queue.json` holding a lite task stops with a message naming `queue.json`. A lite start loads full data and ignores the stored tokens.
- **Queue page.** It opens with a usage strip of session and weekly usage, each with its cutoff, held points and reset, and a Refresh usage action.

## Data directory, time zone and hosts

- **Data directory.** All runtime state sits in one directory with mode 0700: `SESSIONMAXXING_DATA_DIR` (absolute), else `$XDG_DATA_HOME/sessionmaxxing` when `XDG_DATA_HOME` is absolute, else `~/.local/share/sessionmaxxing`. Files: `queue.json`, `dispatch-settings.json`, `session-keeper.json`, `usage-snapshot.json`, `usage-samples.jsonl`, `restart-methods.json`, `runs/`, `restarts/`, `server.lock`. The Compose image mounts the home directory at the same path, so the container uses the same directory as a native run and the lock refuses the second server.
- **One-time move.** A native start moves a `data/` directory found in its working directory to the data directory with one rename (`moveLegacyData`) when it holds `queue.json`, which every dashboard start writes; any other `data/` belongs to another project and stays where it is. It stops with a message naming both paths when the target exists, the legacy directory holds a `server.lock`, it is a symlink, the two paths are nested, or they sit on different filesystems (the message carries the `mv` command). Never merge, copy or delete. Never start a server with the live install's checkout as its working directory while its `data/` is still in place.
- **Time zone.** The server's zone is the process's zone; `TZ` is validated at startup and a value the process did not apply stops it. `GET /api/environment` returns `{ timeZone, workdirRoot, edition }`; the browser formats every time and day boundary in that zone, and analytics, the plan score and the dispatch hour walk take the zone as an argument. Docker sets it through `TZ` in `.env`.
- **Host allowlist.** Requests are accepted when Host is `localhost`, `127.0.0.1`, the bind address, or an entry of `SESSIONMAXXING_ALLOWED_HOSTS` (names or IP literals, no port, path or wildcard); an Origin header must match `http://<Host>`. A wildcard bind (`0.0.0.0`, `::`) approves no address on its own. Compose passes the bind address plus the extra entries.

## Restart methods

A dispatched run cannot restart its own project: it lives inside the dashboard container, and recreating that container would fail every run inside it. The server restarts work directories after applied runs instead, through each directory's restart method. The image carries the docker CLI with the compose and buildx plugins, and `compose.yaml` mounts `/var/run/docker.sock` with the group from `SESSIONMAXXING_DOCKER_GID`. Mounting the docker socket gives any dispatched prompt root on the host. The author accepted this and no socket proxy sits in front of it.

- **Store.** `server/restart-methods.ts` keeps one method per work directory, keyed by its realpath, in `restart-methods.json`: `{ kind: "none" }`, `{ kind: "compose" }` or `{ kind: "command", argv }` with 1 to 64 arguments of 1 to 4096 characters and no NUL or line break. None is never stored; a directory without an entry restarts nothing. `validateRestartMethod` serves the loader and the routes, and a malformed file fails loudly. `GET /api/restart-methods?workdir=` and `PUT /api/restart-methods` (`{ workdir, method }`, None removes the entry) validate the directory with `validateWorkdir`. The task form's Restart select and Command textarea (one argument per line) edit it, and saving the task saves the directory's method.
- **Trigger.** When a run finishes, the runner requests a restart if the run was launched with the apply override, completed, left changes (`leftChanges`) and its directory's method is not None. The record keeps a copy of the method read at that moment.
- **Records.** `server/restarts.ts` stores `restarts/<run id>.json` with `runId`, `title`, `workdir`, `method`, `status`, `requestedAt`, `updatedAt`, `output` and `sibling`. Status is `requested`, `restarting`, `succeeded` or `failed`, and every change is written atomically before the next step starts. `Run.restart` carries `{ status, updatedAt, output }` to the run card (Restart queued, Restarting, Restarted, Restart failed); `output` is sent only for a failed record, capped at its last 64 KiB.
- **Queue block.** While any record is `requested` or `restarting`, `admit()` throws, `select()` picks nothing and every ready gate waits with ``Waits for restart of “<title>”``, because a restart may recreate the dashboard. A finished restart, failed or not, releases the queue. The runner hands a restart to the executor without awaiting it.
- **Execution.** `server/restart-executor.ts` runs records one at a time in request order. Docker Compose runs `docker compose build`, then `docker compose up -d`, in the work directory; Command runs `argv[0]` with the remaining arguments there. Every process is detached and spawned with `shell: false` and without the `SESSIONMAXXING_*` variables, because Compose interpolation prefers the shell environment over the project's `.env`. A step that exits non-zero, cannot start or runs past 30 minutes (SIGTERM to its process group, SIGKILL after two seconds) fails the restart. The record's output is the last 64 KiB of stdout and stderr, then the failure line.
- **Crash recovery.** At start a record left `restarting` without a sibling becomes failed with "Dashboard stopped before the restart finished", and `requested` records run. Closing the server stops the current step and leaves the record as it was.
- **Own project.** With `SESSIONMAXXING_IN_DOCKER=1`, which the image sets, the executor inspects its own container (the hostname) and treats a directory as the dashboard's own project when its realpath equals the container's `com.docker.compose.project.working_dir` label. A missing label or any failed docker call fails the restart, and nothing falls back to an in-place `up -d`. For its own project the executor builds in place, waits until no run is starting or active, records `restarting` with the sibling's name, and starts the detached container `sessionmaxxing-restart-<run id>` from its own image id. The sibling runs as the same user with the socket's group, mounts the socket and the work directory at the same paths, and runs `docker compose up -d`. It is not removed on exit: the running dashboard waits on it with `docker wait`, and a dashboard recreated by it does the same at start, then reads `docker logs`, records succeeded or failed from the exit code, and removes the container with `docker rm`. A sibling still running after 30 minutes fails the record and is removed with `docker rm --force`. A Command on the dashboard's own directory runs in-process and ends failed at the next start when it recreates the dashboard. Native installs have no marker, so no directory is the dashboard's own.
- **Migration.** `server/restart-migration.ts` runs once, when `restart-methods.json` does not exist yet. It stops the start while `deploy/requests/` holds a file, gives every task work directory that exists and holds a Compose file (`compose.yaml`, `compose.yml`, `docker-compose.yaml`, `docker-compose.yml`) the Docker Compose method, imports each `deploy/results/<run id>.json` of a known run as a record (`deploying` becomes failed with "Interrupted before the dashboard took over restarts", a failed result keeps its log as output), and removes `deploy/`. The methods file is written last, so an interrupted migration runs again.

## Concurrency and collisions

- Each running Claude task holds its own expected session percent and `runWeeklyCostPercent` weekly points (default 3, also charged to the Fable window for Fable models) until it finishes. The task being admitted holds nothing yet: the session check adds its own expected cost (rule 3), and the weekly check, plus the Fable check for Fable models, adds its own `runWeeklyCostPercent` (rules 4 and 5), so every run, the first included, must fit with its own cost behind what everything already running holds. Polling folds real consumption into the snapshot while the hold stays, which double counts in the conservative direction.
- Before a task starts, `server/resources.ts` resolves its work directory to lock keys: the realpath of the directory and, when it sits inside a git checkout, the repository's common git dir (linked worktrees and submodules are followed through their `.git` file). Two tasks collide when their paths are equal or nested, or when they belong to the same repository. Worktrees of one repository therefore never run together; separate repositories do. A directory whose repository cannot be resolved waits with a reason rather than running unlocked.
- The runner (`server/runner.ts`) owns the locks in memory. Each tick walks pending tasks in queue order (priority, then creation time), admits each one that passes its gate against the load of running plus already admitted tasks and does not collide with them, and stops when the slots are full. A collided task keeps its place and is reconsidered every tick; later independent tasks may start ahead of it, which is the only way a lower-priority task overtakes a higher one.
- Lock acquisition happens in one synchronous step inside `start()` after resource resolution, before the queue claim, so Run now and the scheduler cannot both take the same slot or resource.
- `PlanningSnapshot.load` reports running counts and held points; each `BucketGate` carries `reserved`; a task gate that waits on a lock carries `blockedBy` with the holder's title. Session ids and resource keys never reach the browser.

## Rules

- Task prompts and work directories are shown in the browser (local-only dashboard). A run's final assistant message is stored as its summary and shown on the run card; everything else — intermediate assistant text, credentials, tokens, UUIDs, raw transcript records, run output — never reaches the browser. The one exception is a failed restart: its output, the last 64 KiB, shows on its run card under Restart output.
- Launch the Claude CLI and every restart process (the docker calls and a Command method) with `child_process.spawn(command, args, { shell: false })`; never build a shell string from a task or a restart method.
- Accept only existing absolute work directories under the work-directory root: `SESSIONMAXXING_WORKDIR_ROOT`, default the running user's home, both realpath'd. A stored task outside a changed root still loads; its run fails with the validation message.
- Dispatched Claude tasks run with `--dangerously-skip-permissions` so a queued run has every tool an interactive session has (shell, web search, MCP servers, skills from `~/.claude`). The container runs unprivileged and only the local queue owner can add tasks, so the prompt is the trust boundary.
- No silent fallbacks: a failed usage fetch is shown as an error and blocks auto-dispatch; corrupt runtime files fail loudly instead of being reset. Two load-time rewrites exist. The provider migration (`server/legacy-provider.ts`) deletes stored Codex tasks and runs, removes ids of deleted tasks from every `dependsOn`, and strips the `provider` key from Claude records; any other provider value fails loudly. The one-time restart migration (`server/restart-migration.ts`) turns the old deploy folder into restart methods and records.
- Restarts run inside the server. Nothing runs as a host service, cron job or daemon; Docker Compose is otherwise started by hand.
- Tests mock only true boundaries (network, clock, process spawning, temp filesystem). Restart tests inject a fake process and never run docker. Never hit the real usage endpoint from tests.
- No "view as table" disclosures, estimate badges, or caveat prose in the UI. The chart is the deliverable.

## Visual direction

Minimal white dashboard: page `#FFFFFF`, a soft grey sidebar `#F7F7F8` with a 20px radius inset 12px from the window edge, and borderless sections separated by whitespace (48px between sections, content at most 1160px wide). Each page opens with a 32px heading, a muted status line and its actions on the right; usage figures sit in KPI rows (label, large number, pace delta, a 6px meter with pace and cutoff marks). Geist for UI text and Geist Mono for prompts, code and work directories; numbers use tabular figures. Ink `#111113` for text and the primary button, muted ink `#62626B` for secondary text, field grey `#F2F2F4` for inputs, secondary buttons and the segmented-control track, hairlines `#E6E6EA` only between list rows. Buttons are 36px with a 10px radius; icon buttons are ghost buttons whose tooltip names the action. Status badges are a colored dot and a label. Soft shadows only on floating surfaces (tooltips, popovers, dialogs, the selected segment, toasts), and area charts fill with fine vertical hatching that fades toward the baseline (`HatchFill`). Series colors keep one meaning on every page: blue `#2E63E6` for usage, local activity and session windows; orange `#D9541E` for the queue (dispatched activity, queue cutoff, quiet hours); teal `#0E8C74` for Fable only; violet `#7B5CE0` and magenta `#C2338A` for further models, in that order; grey `#8B8B94` for pace, unattributed and other sources; ink for now markers. Green `#15793A` only for success, ready and running, amber `#A0590A` for waiting and attention, red `#C4281F` for errors. A dark theme swaps the same tokens (page `#0E0E10`, sidebar `#161619`, raised `#1B1B1F`, light ink, and dark-surface steps of each series color) through `data-theme="dark"` on `<html>`: an inline script in `app/layout.tsx` sets it before first paint from the stored choice or the system setting, and the sidebar's Dark mode button stores a choice. `app/lib/palette.ts` holds both palettes; `tests/palette.test.ts` checks text contrast (4.5 on every surface and on each status tint `app/styles.css` mixes), series contrast (3 on the page) and that `app/styles.css` matches the palette. Components read colors through `var(--token)`, never hex. shadcn's `.dark` class is never set. `app/components/ui/` stays untouched; colors come from tokens in `app/styles.css` and shape from `[data-slot]` rules in its unlayered block.
